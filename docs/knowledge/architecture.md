# Architecture

## Crate layering

`cpu_rasteriser` depends on `rasteriser_macros`. `engine` depends on both. `cpu_rasteriser` knows nothing about windows, scenes or assets. Its output is a `RenderTarget` whose pixels the caller reads (`pixels`, `pixels_u32`, `write_pixels`, `write_pixels_u32`).

`cpu_rasteriser` re-exports `wide` (`pub use wide`) because the code generated by `#[derive(SimdInterpolate)]` refers to `::cpu_rasteriser::wide::f32x8`. A user crate therefore doesn't need its own `wide` dependency.

`prelude` is the intended import surface for users: `use cpu_rasteriser::prelude::*`. Most modules are also `pub` (`framebuffer`, `depthbuffer`, `graphics::*`). Benches depend on that, but it exposes internals such as `FrameBuffer` and `Triangle2D` more widely than users need.

## Render-pass lifecycle

All rendering goes through one flow in `renderer.rs`:

1. **`Renderer::begin_render_pass(&mut target, RenderPassDescriptor)`** borrows the renderer mutably, so only one pass can exist at a time. It immediately builds a `TileBinner` for the whole target. Each tile takes a colour buffer, and optionally a depth buffer, from the renderer's tile pool, seeded from the pass's load operations. See `tiling-and-threading.md`.
2. **`RenderPass::draw` / `draw_simd`** only queue work. Each call boxes a `QueuedDraw` or `QueuedDrawSimd` as a `Box<dyn RenderPassCommand>`. The trait object erases the pipeline's shader types, so one pass can mix any number of pipelines, scalar and SIMD alike.
3. **`RenderPass::finish`** runs in two stages:
   1. *Serial, on the calling thread:* for each queued draw, in submission order:
      1. assemble triangles from the index buffer;
      2. run the vertex shader, clip, convert to screen space and cull (`GeometryProcessor::process_triangle`);
      3. wrap each surviving screen triangle in an `Arc<dyn RasterCommand>`, which carries the fragment shader, the fragment uniforms, and the blend and depth state;
      4. bin it into every tile it may overlap.
   2. *Parallel:* each tile becomes one job on the `threadpool`. A job rasterises the tile's commands in order into the tile's own buffers. Finished tiles come back over an mpsc channel and are copied into the render target on the calling thread.

Data ownership across that boundary:

| Owner | Contents |
|---|---|
| Pipeline | Vertex shader by value; fragment shader in an `Arc` so raster commands can share it |
| Draw call | Borrows the vertex and index slices for the pass's lifetime (`'pass`) |
| Per draw call | Fragment uniforms moved into one `Arc`, shared by all of that draw's triangles |
| Per draw | Vertex uniforms passed by value |

## Two pipeline types

`Pipeline<VS, FS>` (scalar) and `SimdPipeline<VS, FS>` (8-wide) share a private `PipelineState`, which holds culling, an optional blend state and the depth state. Their builder methods (`with_culling_mode`, `with_blend_state`, `without_blend_state`, `with_depth_state`) are duplicated between the two types.

The defaults are `CullingMode::BackFace`, no blending and `DepthState::DISABLED`. Depth testing must be switched on explicitly.

The two paths share everything up to rasterisation: queuing, geometry processing, binning and merging. They diverge only in the `RasterCommand` implementation (`TriangleRasterCommand` or `TriangleRasterCommandSimd`). See `simd.md`.

## Shader model

- `VertexShader` has associated `Vertex`, `Uniforms` and `Varyings` types. It returns a clip-space `Vec4` and the varyings.
- `FragmentShader<V>` and `FragmentShaderSimd<V>` are generic over the varying type. They are independent of each other: a shader can implement either one or both.
- `Varyings` must implement `Interpolate`, and for the SIMD path also `SimdInterpolate`. Both are usually derived.
- Raster commands cross into worker threads inside `Arc`s, so shaders, uniforms and varyings must be `Send + Sync + 'static`.
  - `VertexShader` and `FragmentShader` require this as supertraits.
  - `FragmentShaderSimd` requires it only of its `Uniforms`; `draw_simd` adds the rest of the bounds where it is called.

## Engine on top

`engine::app` defines the `Application` trait. Its `RenderContext` exposes `begin_render_pass` (any target) and `begin_presentation_pass`. It returns a `PresentationPass` over the backend-owned presentation target, and its `finish` returns the `PresentedFrame` proof token. See `engine.md`.
