# SIMD path

The SIMD path uses portable SIMD from the `wide` crate (`f32x8`), not `std::arch` intrinsics. Eight lanes assume AVX for full speed, which is why `target-cpu=native` matters (see `testing-and-benchmarks.md`). Without it, `wide` falls back to narrower instructions.

## Selection

The path is selected at compile time per draw. `SimdPipeline` plus `RenderPass::draw_simd` produces a `TriangleRasterCommandSimd`. There is no runtime dispatch and no automatic fallback.

`FragmentShaderSimd` is independent of `FragmentShader`: `SimdPipeline`'s bounds only require `FragmentShaderSimd`.

## Rasterisation (`Triangle2D::rasterise_segment_simd`)

- **Same as scalar:** the edge setup and coverage rules are the scalar ones (see `geometry-and-rasterisation.md`).
- **Spans:** each span is processed in groups of 8 consecutive pixels starting at `x_start`. Groups are **not aligned** to multiples of 8.
- **Tail:** the last partial group uses `mask_for_lanes(remaining)`. Lane masks are `f32x8` values holding all-ones bit patterns.
- **Interpolation:** lane values come from `SimdInterpolate::simd_step` (base + lane index × step). Each group advances with `simd_add_scaled` by 8 steps, and `simd_perspective` applies perspective correction.
- **Masked lanes still compute values.** The fragment shader runs on all 8 lanes, including masked-out ones whose varyings are extrapolated beyond the triangle. SIMD shaders must be safe on such inputs. The engine's texture SIMD samplers clamp UVs, so they are.

## Raster command (`TriangleRasterCommandSimd`)

`rasterise_impl` is monomorphised over const generics `<TEST_DEPTH, WRITE_DEPTH>`, dispatched once per command from `DepthState`. This removes the per-group depth branches. Per group:

1. **Depth test:** an unaligned 8-wide depth load, `pass = mask & (depth < stored)`. If no lane passes, the group stops here.
2. **Shading:** `shade_simd` runs.
3. **Blending (optional):** an 8-wide colour load, then `BlendState::apply_simd`.
4. **Colour write:** one scalar store per passing lane, `set_pixel_index_unchecked`. The framebuffer is an array of `Colour` structs (AoS), so there is no vector store.
5. **Depth write:** `set8_unchecked_with_mask` performs a read-select-write over all 8 slots.

## The padding invariant behind the unchecked accesses

`FrameBuffer` and `DepthBuffer` store their data in a `Grid`, whose `stride_for` uses `stride = (width + 7).next_multiple_of(8)`. That guarantees `x + 8 ≤ stride` for every `x < width`. An 8-wide access starting at any in-bounds pixel therefore stays within that row's allocation.

Tile buffers are separate allocations with their own padded stride, so the invariant holds in tile-local coordinates. Pooled tile buffers recompute the stride whenever they are resized for a new pass.
- Lanes past the row's logical width read and write padding.
- The masked depth write rewrites lanes between the span end and the group end with their own current values. This is benign only because a tile is single-threaded.

Any change to buffer layout, tile size or group alignment must preserve this. The stride padding was introduced in PR #17 (commit `44b39b2`) after the earlier unchecked accesses were wrong.

## `#[derive(SimdInterpolate)]` (`rasteriser_macros`)

- **Output:** it generates `<Name>Simd`, with one `f32x8` per scalar component, and the `SimdInterpolate` implementation.
- **Field types:** only `f32`, `Vec2`, `Vec3` and `Vec4` are supported. They are matched by the **last path segment's name**, so a type alias or another type with the same name is accepted or rejected purely by name.
- **Visibility:** the generated struct takes the visibility of the source struct, but its **fields are private**. SIMD shaders must therefore be written in the same module as the varying struct.
- **Hygiene:** code generated by both derives names traits and types without paths. `#[derive(Interpolate)]` uses `Interpolate`; `#[derive(SimdInterpolate)]` uses `SimdInterpolate`, `Vec2`, `Vec3` and `Vec4`. Those names must therefore be in scope wherever either derive is used, usually through the prelude.
- **Unused trait:** `SimdInterpolateField` (`interpolate.rs`) is implemented for `f32` but is used neither by the macro nor anywhere else. It is crate-private and marked `#[expect(dead_code)]`.
- **Tests:** the derive's `::cpu_rasteriser::` paths resolve inside `cpu_rasteriser` itself only in test builds, through `#[cfg(test)] extern crate self as cpu_rasteriser` in `lib.rs`; the `renderer.rs` tests use the derive. The unit tests in `graphics/triangle.rs` still implement `SimdInterpolate` by hand. The benches are separate crates where the derive would work, but they also implement it by hand.

## Known SIMD/scalar divergence

Blending and alpha behave differently on the two paths (see `buffers-and-colour.md`), and `rasterise_simd_matches_scalar` currently fails ([#21](https://github.com/costott/cpu_rasteriser/issues/21)).
